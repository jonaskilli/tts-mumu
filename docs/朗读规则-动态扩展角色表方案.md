# 朗读规则：动态扩展角色表方案

> 目标：配置项数量超过朗读规则 JS 硬编码的批量角色数量时，自动扩展角色表，免去手动去朗读规则加标签。
> 关联文件：`tts配套文件/ttsrv-speechRule-多角色朗读2.87【加速版+1修复2.2】.js`
> 状态：**已实施**（2026-08-04）

---

## 一、问题背景

### 1.1 现象

系统TTS列表里「女青年」配置项有 400 个，但朗读规则 JS 只硬编码了 100 个女青年角色。新增的「女青年101~400」配置项：

- `getTagName` 走「其他标签」分支，返回旁白或映射名，**tagName 显示异常**
- `detectAvailableVoices` 遍历 `GENSHIN_CHARACTERS`（只有100个）时漏掉这些 tag，**发音人被标记无效**

用户每次新增配置项都要手动去朗读规则 JS 里加标签，无法维护。

### 1.2 根因

朗读规则的角色数量是 JS 里 `BATCH_ROLES` 硬编码（[第76行](file:///workspace/tts配套文件/ttsrv-speechRule-多角色朗读2.87【加速版+1修复2.2】.js#L76) `['女/女青年', '女', '女青年', '女青年', 100]`），而配置项数量由用户在系统TTS列表动态添加。**两者不同步**，JS 表跟不上配置项增长。

### 1.3 数据流（核对自代码）

```
配置项(DB system_tts_v2)
  └─ speechRuleInfo.tag = "女青年101"
        │ app SpeechRuleEngine.handleText()
        │   把 List<SpeechRuleInfo> 转成 tagsDataMap：key=tag, value=tagData
        ▼
JS handleText(text, tagsData)
  └─ tagsData = { "女青年01": {...}, ..., "女青年101": {...}, "女青年400": {...} }
        │ detectAvailableVoices(tagsData)
        │   遍历 GENSHIN_CHARACTERS（仅女青年01~100）
        │   检查 tagsData[voiceTag] 是否存在
        ▼
  女青年01~100 → availableVoices ✓
  女青年101~400 → 不在 GENSHIN_CHARACTERS 中 → 漏掉 ✗
```

**关键**：`detectAvailableVoices` 是以 `GENSHIN_CHARACTERS` 为索引遍历的，`tagsData` 里多余的 key（女青年101~400）不会被主动扫描。所以光有 tagsData 不够，必须让 `GENSHIN_CHARACTERS` 也包含这些角色。

---

## 二、方案原理

### 2.1 核心思路

在 `handleText` 入口、`detectAvailableVoices` 调用之前，**反向扫描 `tagsData` 的 key（即配置项 tag）**，对形如「前缀+序号」的 tag，按需补齐 `GENSHIN_CHARACTERS` 和 `SpeechRuleJS.tags`。

### 2.2 三个阶段

**阶段1：统计现有最大序号**

遍历 `GENSHIN_CHARACTERS`，对每个角色的 `voice`（如"女青年01"）用正则 `/^([\u4E00-\u9FA5]+?)(\d+)$/` 解析出前缀和序号，记录每个 BATCH_ROLES 前缀的现有最大序号。

```
女青年01~100 → batchPrefixMaxSeq["女青年"] = 100
男青年01~100 → batchPrefixMaxSeq["男青年"] = 100
```

**阶段2：扫描 tagsData 找需求**

遍历 `tagsData` 的 key（配置项 tag），同样用正则解析，记录每个前缀需要的最大序号。

```
tagsData 包含 女青年101~400 → neededMaxSeq["女青年"] = 400
```

**阶段3：按需补齐**

对每个前缀，从 `curMax+1` 循环到 `needMax`，生成角色对象加入 `GENSHIN_CHARACTERS`，同时把 voice 标签加入 `SpeechRuleJS.tags`。

```javascript
for (ni = 101; ni <= 400; ni++) {
    nSeq = padZero(ni, 2);              // "101"
    nName = '【女青年101】';
    nVoice = '女青年' + nSeq;            // "女青年101"
    GENSHIN_CHARACTERS[nName] = { gender:'女', age:'女青年', voice: nVoice };
    SpeechRuleJS.tags[nVoice] = nName;
}
```

### 2.3 关键设计

| 设计点 | 做法 | 原因 |
|---|---|---|
| **前缀白名单** | 只处理 `BATCH_ROLES` 里已定义的前缀 | 避免误伤自定义 tag（如"特殊男1"），只扩展已知批量角色类型 |
| **增量扩展** | 只补 `curMax+1` 到 `needMax` | 不重复生成已有的，避免覆盖 |
| **幂等** | 扩展后更新 `batchPrefixMaxSeq` | 同一次 handleText 内不重复扩展 |
| **异常兜底** | 整段 try-catch | 扩展失败不影响后续 handleText 正常执行 |
| **生效时机** | 在 `detectAvailableVoices` 之前 | 保证 availableVoices 正确包含新角色 |
| **ES5 兼容** | var、for 循环、hasOwnProperty | Rhino 引擎不支持 ES6+ |

### 2.4 前缀来源

前缀白名单从 `BATCH_ROLES` 配置动态提取，不硬编码：

```javascript
BATCH_ROLES = [
  ['女/女青年', '女', '女青年', '女青年', 100],  // 前缀="女青年"（取'/'后一段）
  ['男/男青年', '男', '男青年', '男青年', 100],
  ...
];
```

`bType.substring(bType.lastIndexOf('/') + 1)` 把 `"女/女青年"` 转成 `"女青年"`，与 voice 前缀一致。这样后续 BATCH_ROLES 增删角色类型时，扩展逻辑自动跟随，无需改这段代码。

## 三、实施细节

### 3.1 插入位置

`handleText` 函数入口（[3293行](file:///workspace/tts配套文件/ttsrv-speechRule-多角色朗读2.87【加速版+1修复2.2】.js#L3293)），在 `forceFlattenArray`/`isArray` 辅助函数定义之后、音效正则处理之前。位于 [3317-3384行](file:///workspace/tts配套文件/ttsrv-speechRule-多角色朗读2.87【加速版+1修复2.2】.js#L3317)。

### 3.2 完整代码

```javascript
// ========== 动态扩展角色表（方案2）==========
try {
    // 1. 统计每个 BATCH_ROLES 前缀在 GENSHIN_CHARACTERS 中的现有最大序号
    var batchPrefixMaxSeq = {};
    var batchPrefixInfo = {};
    for (var bi = 0; bi < BATCH_ROLES.length; bi++) {
        var bItem = BATCH_ROLES[bi];
        var bPrefix = bItem[0].substring(bItem[0].lastIndexOf('/') + 1);
        batchPrefixInfo[bPrefix] = { gender: bItem[1], age: bItem[2], voicePre: bItem[3] };
        batchPrefixMaxSeq[bPrefix] = 0;
    }
    for (var gName in GENSHIN_CHARACTERS) {
        if (GENSHIN_CHARACTERS.hasOwnProperty(gName)) {
            var gMatch = GENSHIN_CHARACTERS[gName].voice.toString().match(/^([\u4E00-\u9FA5]+?)(\d+)$/);
            if (gMatch && batchPrefixMaxSeq.hasOwnProperty(gMatch[1])) {
                var gSeq = parseInt(gMatch[2], 10);
                if (gSeq > batchPrefixMaxSeq[gMatch[1]]) {
                    batchPrefixMaxSeq[gMatch[1]] = gSeq;
                }
            }
        }
    }
    // 2. 扫描 tagsData 的 key，找出每个前缀需要扩展到的最大序号
    var neededMaxSeq = {};
    for (var tdKey in tagsData) {
        if (tagsData.hasOwnProperty(tdKey)) {
            var tdMatch = tdKey.match(/^([\u4E00-\u9FA5]+?)(\d+)$/);
            if (tdMatch && batchPrefixInfo.hasOwnProperty(tdMatch[1])) {
                var tdSeq = parseInt(tdMatch[2], 10);
                if (!neededMaxSeq[tdMatch[1]] || tdSeq > neededMaxSeq[tdMatch[1]]) {
                    neededMaxSeq[tdMatch[1]] = tdSeq;
                }
            }
        }
    }
    // 3. 按需补齐 GENSHIN_CHARACTERS 和 SpeechRuleJS.tags
    for (var extPrefix in neededMaxSeq) {
        if (neededMaxSeq.hasOwnProperty(extPrefix)) {
            var extInfo = batchPrefixInfo[extPrefix];
            var curMax = batchPrefixMaxSeq[extPrefix];
            var needMax = neededMaxSeq[extPrefix];
            if (needMax > curMax) {
                for (var ni = curMax + 1; ni <= needMax; ni++) {
                    var nSeq = padZero(ni, 2);
                    GENSHIN_CHARACTERS['【' + extPrefix + nSeq + '】'] = {
                        gender: extInfo.gender, age: extInfo.age,
                        voice: extInfo.voicePre + nSeq
                    };
                    SpeechRuleJS.tags[extInfo.voicePre + nSeq] = '【' + extPrefix + nSeq + '】';
                }
                batchPrefixMaxSeq[extPrefix] = needMax;
            }
        }
    }
} catch (extErr) {
    console.error("动态扩展角色表异常: " + extErr.message);
}
// ========== 动态扩展结束 ==========
```

## 四、效果与验证

### 4.1 效果

| 场景 | 之前 | 之后 |
|---|---|---|
| 女青年101~400 配置项 | tagName 异常、发音人无效 | 自动扩展角色表，正常识别 |
| 男青年、少女等其他前缀 | 同上 | 同样自动扩展 |
| 自定义 tag（非 BATCH_ROLES 前缀） | 不受影响 | 不受影响（白名单过滤） |
| BATCH_ROLES 内 100 个以内 | 正常 | 正常（needMax ≤ curMax，不扩展） |

### 4.2 验证方法

1. 添加「女青年101」「女青年102」配置项，tag 填 `女青年101`、`女青年102`
2. 运行朗读，观察这两个发音人是否被正确分配（不⚠、不退化为旁白）
3. 查看角色列表标签显示是否正常（配合方案A的 generateVoiceTag 显示 voice）

### 4.3 局限

- **只处理 BATCH_ROLES 定义的批量角色前缀**：主角（MAIN_ROLES_CONFIG）、特殊角色（SPECIAL_ROLES）不在扩展范围。若用户超额添加主角配置项，需类似逻辑扩展 MAIN_ROLES_CONFIG。
- **序号格式要求**：tag 必须是「中文前缀+数字」格式（如`女青年101`），纯名字（如`晓晓`）不会被扩展。
- **性能**：每次 handleText 都会扫描一次 tagsData。配置项数量大时（如400个）有轻微开销，但相比后续的文本正则处理可忽略。

## 五、后续其他朗读规则修改参考

本方案可作为**「JS 硬编码与 app 动态数据不同步」**类问题的通用处理范式：

### 5.1 适用场景

- 角色数量、发音人数量等 JS 硬编码值，跟不上 app 侧用户动态配置
- JS 表结构作为索引遍历（如 `detectAvailableVoices` 遍历 `GENSHIN_CHARACTERS`），光补 app 侧数据不够，必须同步补 JS 表

### 5.2 通用步骤

1. **定位硬编码源**：找 JS 里写死的数量/列表（如 `BATCH_ROLES` 的 count 字段）
2. **定位索引遍历点**：找以 JS 表为索引的遍历逻辑（如 `detectAvailableVoices`）
3. **确定 app 传入的数据载体**：找 handleText 等入口收到的、包含动态数据的参数（如 `tagsData`，key 是配置项 tag）
4. **在遍历点之前插入反向扫描**：从 app 数据反推出需要的数量，按需补齐 JS 表
5. **白名单约束**：只处理已知前缀/类型，避免误伤自定义数据
6. **增量+幂等**：只补差额，更新基准值避免重复
7. **异常兜底**：try-catch 包裹，扩展失败不影响主流程

### 5.3 类似可优化的点（待定）

- `MAIN_ROLES_CONFIG`（主角）：若用户超额添加男主/女主配置项，可仿此扩展
- `tagsData` 的 `duihua` 配置：角色名/性别年龄的动态读取（4334行附近）已有类似思路，可参考
- `fayinren.json` 生成（4478行附近）：若要让存储键统一为 name，可参考本方案的反向扫描思路

### 5.4 注意事项

- **ES5 兼容**：Rhino 引擎不支持 ES6+，避免用 `let`/`const`/`for...of`/箭头函数/模板字符串
- **hasOwnProperty 检查**：遍历对象时务必检查，避免遍历到原型链属性
- **正则中文匹配**：`[\u4E00-\u9FA5]` 匹配基本汉字，扩展汉字（如罕见字）需用 `\u4E00-\u9FFF`
- **插入位置**：必须在索引遍历点（如 `detectAvailableVoices`）之前，否则补齐无效
- **测试覆盖**：边界情况（序号不连续、序号小于现有、非数字后缀、空 tagsData）都要验证
