## 乌龙根因复盘（19:45 定案）⚠️
**真凶：.git 的 ref 落盘静默失败**——packed-refs 里 remotes/origin/mumu_tts_github 残留旧值 afee10c（3acc962 的祖先），此后 fetch/push/update-ref 全部"声称成功"但 loose ref 文件写不进去（git 写路径被吞，直接 shell echo 写文件却正常），本地 git 长期"以为"远端在 afee10c → reset --soft 错位 → force push 拉回祖先。手动 `echo <sha> > .git/refs/remotes/origin/mumu_tts_github` 修复，fsck 干净，ref 稳定不回滚（NTFS、非 reftable，瞬时写入丢失具体机制未能实锤，怀疑杀软/锁）。
**规则**：本地与远端一致性核验必须用 `git ls-remote`（直问远端）而非本地跟踪 ref；发现跟踪 ref 与 ls-remote 不符时先查 packed-refs + loose 文件是否一致再下结论。当前状态：本地=远端=4030836，fsck 干净。

## ref 写入故障精确定位（19:55 定案）⚠️ 环境级
**症状**：`git update-ref` / `git fetch`（带不带 refspec 都一样）对 `refs/remotes/**` 的更新**声称成功(exit0)但从不落盘**；`refs/heads/**` 写入正常。故 remote-tracking ref 永远读 packed-refs 里的旧值 → 造成今日整场乌龙。
**关键实验**：heads 写 probe 成功落盘；remotes 写 probe 失败；手动 `echo sha > .git/refs/remotes/origin/xxx` 能写且 git 能读到 → 不是权限问题，是 **git 的 ref 写入流程（创建 xxx.lock → 写 → rename）被拦截**（rename 环节被吞，与杀软/文件筛选驱动典型特征吻合）。目录不存在时 git 也不会自建 remotes/origin。
**应急修法**：直接改 `.git/packed-refs` 里对应两行（heads + remotes/origin 的分支 sha），立刻生效；此后核验一律用 `git ls-remote` 直问远端。
**根治方案**：①给 E:/TTS 加杀软白名单后复测；②重新 clone 一份 .git 替换（工作区干净时零风险）。
