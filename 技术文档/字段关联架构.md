# 字段关联架构

> 目标：梳理 tag / tagName / voice / displayName / gender / configId / tagData 等字段在朗读规则（JS）与 app 端（Kotlin）之间的定义、填充、传递与匹配关系。这些字段跨多文件、多层调用，命名相近且存在隐式约定，不易捋清，故统一记录。
> 关联文件：
> - 字段定义：`lib-database/src/main/java/com/github/jing332/database/entities/systts/SpeechRuleInfo.kt`
> - 字段填充：`app/src/main/java/com/github/jing332/tts_server_android/service/systts/help/TextProcessor.kt`
> - JS引擎桥接：`app/src/main/java/com/github/jing332/tts_server_android/model/rhino/speech_rule/SpeechRuleEngine.kt`
> - 朗读规则：`tts配套文件/` 目录下的朗读规则 JS
> 状态：**现行**（2026-08-08）

## 一、字段定义层（SpeechRuleInfo）

`SpeechRuleInfo` 是发音人配置中"朗读规则相关字段"的载体，存储在数据库 `SystemTtsConfig.speechInfo` 里。

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `target` | Int | 朗读目标（ALL/对话框/旁白等） | 0=ALL |
| `isStandby` | Boolean | 是否备用发音人 | false |
| `specifiedStandbyId` | Long? | 指定备用ID（同标签备用） | null |
| `tag` | String | **发音人标签**（连接JS与app的核心键） | "女青年01"、"duihuaA"、"括号4" |
| `tagRuleId` | String | 标签规则ID（对应朗读规则的ruleId） | "mingwuyan" |
| `tagName` | String | 标签显示名 | "『对话旁白』" |
| `tagData` | Map<String,String> | 标签数据（键值对） | {role:"张三", genderAge:"男青年"} |
| `configId` | Long | **配置项ID**（数据库主键，唯一标识） | 42 |
| `voice` | String | **底层发音人voice**（TTS引擎实际标识） | "zh-CN-XiaoxiaoNeural" |
| `displayName` | String | **显示名称**（用户可见名） | "晓晓" |

### 核心区分

- **tag vs voice**：tag 是朗读规则里的逻辑标签（如"女青年01"），voice 是TTS引擎的底层标识（如"zh-CN-XiaoxiaoNeural"）。多个配置可以共用同一个tag（如10个"女青年01"），但每个配置的voice/configId不同。
- **tag vs tagName**：tag 是内部键（"括号4"），tagName 是给人看的显示名（"『对话旁白』"）。
- **voice vs displayName**：voice 是引擎底层标识（程序用），displayName 是用户起的名字（人用）。
- **configId**：唯一标识一个数据库配置项，用于精确匹配。

## 二、字段填充层（TextProcessor → SpeechRuleInfo）

`TextProcessor.getTextList()` 从 `SystemTtsConfig` 构造 `SpeechRuleInfo`：

```kotlin
// TextProcessor.kt 第64-71行
val systts = cfg.tag as? SystemTtsV2
SpeechRuleInfo(
    configId = entry.key,                          // ← 数据库主键
    voice = cfg.source.voice,                      // ← TTS引擎底层voice
    displayName = systts?.displayName ?: "",       // ← 用户可见名
    // tag/tagRuleId/tagName/tagData 来自 cfg.speechInfo 已有字段
)
```

### 字段来源映射

| SpeechRuleInfo字段 | 来源 |
|-------------------|------|
| configId | 数据库 entry.key |
| voice | cfg.source.voice（TTS引擎配置） |
| displayName | (cfg.tag as SystemTtsV2).displayName |
| tag | cfg.speechInfo.tag（用户在UI配置的标签） |
| tagRuleId | cfg.speechInfo.tagRuleId |
| tagName | cfg.speechInfo.tagName |
| tagData | cfg.speechInfo.tagData |
| isStandby | cfg.speechInfo.isStandby |

## 三、JS引擎桥接层（SpeechRuleEngine）

`SpeechRuleEngine.handleText()` 把 `List<SpeechRuleInfo>` 转成 `tagsDataMap` 传给 JS：

```kotlin
// SpeechRuleEngine.kt 第86-120行
fun handleText(text: String, list: List<SpeechRuleInfo>): List<TextWithTag> {
    val tagsDataMap = mutableMapOf<String, ...>()
    list.forEach { info ->
        // 1. tagData 注入（按tag分组）
        tagsDataMap[info.tag][tagDataKey] += [{ id: configId, value: tagDataValue }]
        
        // 2. 方案B：底层 voice 注入（key="_voice"）
        tagsDataMap[info.tag]["_voice"] += [{ id: configId, value: voice }]
        
        // 3. 方案B：displayName 注入（key="_displayName"）
        tagsDataMap[info.tag]["_displayName"] += [{ id: configId, value: displayName }]
    }
    // 调用 JS handleText(text, tagsDataMap)
}
```

### tagsDataMap 结构

```
tagsDataMap = {
    "女青年01": {
        "role":       [{ id: 42, value: "张三" }, { id: 43, value: "李四" }],
        "genderAge":  [{ id: 42, value: "女青年" }],
        "_voice":     [{ id: 42, value: "zh-CN-XiaoxiaoNeural" }],
        "_displayName":[{ id: 42, value: "晓晓" }]
    },
    "duihuaA": {
        "_voice":     [{ id: 50, value: "zh-CN-YunxiNeural" }],
        "_displayName":[{ id: 50, value: "云希" }]
    }
}
```

JS 侧通过 `tagsData[tag]._voice`、`tagsData[tag]._displayName` 访问这两个字段（下划线前缀避免与正常 tagData 冲突）。

### JS 返回值（TextWithTag）

JS 处理后返回 `List<TextWithTag>`：

| 字段 | 说明 |
|------|------|
| text | 分割后的文本片段 |
| tag | **发音人标签**（正常情况）或 **voice值**（方案B特殊场景，见第六节） |
| id | configId（JS 从 tagsDataMap 透传，用于精确匹配） |

## 四、JS 内部字段体系

### 4.1 tags 对象（tag → tagName 映射）

```javascript
tags: {
    narration: "旁白",
    duihua: "对话",
    duihuaA: "男",
    duihuaB: "女",
    "括号1": "【】括号发音人",
    "括号4": "『』括号发音人",
    // GENSHIN_CHARACTERS 动态生成：男主1, 女主01, 男青年01...
}
```

- **作用**：tag 到 tagName 的映射，`getTagName()` 优先用 JS 的这个对象，失败则用 app 端 `SpeechRuleInfo.tagName`。

### 4.2 tagsData 对象（运行时数据）

JS 运行时从 Kotlin 注入的数据，按 tag 分组，包含 tagData + _voice + _displayName。

### 4.3 角色配置表

| 表 | 结构 | 用途 |
|----|------|------|
| GENSHIN_CHARACTERS | [name, gender, age, tag] | 原神角色，动态生成tag |
| BATCH_ROLES | 批量角色定义 | 男青年01-100等批量tag |
| SPECIAL_ROLES | [tagName, gender, age, tag] | 括号1-4等特殊角色 |

### 4.4 gender 字段（JS内部）

gender 是 JS 内部的角色性别字段，**不在 SpeechRuleInfo 里**，决定分配哪个tag：

| gender | 分配的tag类型 |
|--------|-------------|
| "男" | 男主/男青年/男中年/男老年/男童/少年 |
| "女" | 女主/女青年/女中年/女老年/女童/少女 |
| "特殊" | 特殊男/特殊女/括号1/括号4 |
| "特" | 括号2/括号3 |
| ""（空） | 兜底走duihua（密钥失效时） |

## 五、匹配层（TextProcessor 匹配逻辑）

JS 返回 `List<TextWithTag>` 后，app端为每个片段匹配发音人配置：

```kotlin
// TextProcessor.kt 第140-152行
val sameTagList = configs.filter { !isStandby && tag == txtWithTag.tag }
val config = configFromId                                    // 1. 精确匹配ID
    ?: sameTagList.randomOrNull(random)                      // 2. tag内随机
    ?: configs.filter { !isStandby && voice == txtWithTag.tag }  // 3. voice匹配(方案B)
       .randomOrNull(random)
    ?: configs.randomOrNull(random)                          // 4. 全局随机
```

### 匹配优先级

| 优先级 | 条件 | 说明 |
|--------|------|------|
| 1 | `configId == txtWithTag.id` | 精确匹配：JS透传的configId |
| 2 | `tag == txtWithTag.tag`（同tag列表内随机） | tag匹配：同标签内随便选一个 |
| 3 | `voice == txtWithTag.tag`（方案B） | **voice匹配**：见第六节隐式约定 |
| 4 | 全局随机 | 兜底：随便选一个 |

## 六、关键隐式约定（易混淆点）

### 6.1 txtWithTag.tag 的双重含义（方案B）

**这是最容易混淆的点**：JS 返回的 `TextWithTag.tag` 字段，在正常情况下是发音人标签（如"女青年01"），但在方案B的特定场景下，会放入 **voice 值**（如"zh-CN-XiaoxiaoNeural"）。

匹配层第3步 `voice == txtWithTag.tag` 就是处理这种情况——当 tag 匹配失败时，尝试用 txtWithTag.tag 当作 voice 去匹配配置项的 voice 字段。

| 场景 | txtWithTag.tag 的值 | 匹配命中 |
|------|---------------------|---------|
| 正常 | "女青年01"（tag） | 第1/2步 |
| 方案B特殊 | "zh-CN-XiaoxiaoNeural"（voice） | 第3步 |

### 6.2 _voice / _displayName 的下划线前缀

Kotlin 注入 tagsDataMap 时，voice 和 displayName 用 `_voice`、`_displayName` 作为 key（下划线前缀），避免与正常 tagData 的 key（如 role、genderAge）冲突。JS 侧必须用 `tagsData[tag]._voice` 访问。

### 6.3 tagRuleId 的作用

`tagRuleId` 标识使用的是哪条朗读规则（对应 `SpeechRuleEngine.ruleId`）。同一套 tag（如"女青年01"）在不同朗读规则下含义可能不同，tagRuleId 用于区分。

### 6.4 configId 的透传

configId 在 `tagsDataMap` 里作为每条数据的 `id` 字段，JS 处理后会把它透传到返回的 `TextWithTag.id`。app端用这个 id 做精确匹配（匹配优先级第1步）。如果 JS 无法确定具体configId（如随机分配），id 可能为0，此时走第2步tag内随机。

### 6.5 isStandby 在匹配时的过滤

匹配发音人时，`isStandby=true` 的配置会被过滤掉（第1/2/3步都带 `!isStandby`）。备用发音人只在 `standbyConfig` 切换时使用，不参与正常分配。
