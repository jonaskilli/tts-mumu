# 播放管线技术研究（2026-08-18）

---

## 一、完整播放链路

### 模式 A：系统 TTS 服务（不开转发器，搭配朗读规则多角色）

```
阅读App → Android TTS API
  → SystemTtsService.onSynthesize(text)
    → MixSynthesizer.synthesize()
      → init(): 加载配置 + 引擎预热 + 文本处理器init(JS规则引擎eval)
      → executeSynthesis():
          → textProcess(): 朗读规则JS splitText → segments[{text, tts}]
          → produce channel(cap=32):
              for 每段:
                预取段N+1请求(Dispatchers.IO)  ← 0818新增
                requestAndProcess(段N):
                  → DefaultTtsRequester.request()
                      → CachedEngineManager.getEngine() (10min缓存)
                      → 合并配置项audioParams到SystemParams
                  → DefaultResultProcessor.processStream()
                      → 解码(裸PCM直读/MP3走ExoPlayer) 
                      → 管线[静音跳过?]→[Sonic?]→[响度?]  ← 0818条件化
                      → callback(pcm)
                  → channel.trySendBlocking(pcm)  ← 0818改，有背压
          → 消费端 for payload in channel:
              → onSynthesizeAvailable(pcm)
                → writeToCallBack → callback.audioAvailable → AudioTrack(最终背压源)
```

### 模式 B：转发器

```
同上管线，但消费端 SysTtsForwarderService 用 ByteArrayOutputStream
累积全部PCM → 合成完写WAV文件 → 交给阅读App
（文件交付模式，无法边合成边播，预取已加速合成本身）
```

## 二、音频参数叠加体系

**计算位置**：TtsRepository，乘法叠加：

```
最终值 = 插件级(source滑块) × 配置项级 × [子分组级×分组级×全局级-已废弃]
```

**0818 修复**：PluginTtsProvider 原逻辑 source 级(默认1f)直接**覆盖**配置项级导致配置项参数无效，改为相乘：
- source=1f → 配置项参数完整生效
- source=1.5, 配置项=1.2 → 实际1.8
- source=0f(FOLLOW) → 只用叠加值

本地 TTS（LocalTtsProvider）无此问题，直接用 params.speed。

## 三、引擎缓存机制

- CachedEngineManager：10分钟空闲过期，每1分钟清理
- 0818 起 init() 预热所有引擎（onInit），首请求不再付初始化成本
- **重试路径仍会销毁重建引擎**（retry() → removeEngine → 下次getEngine重新create+onInit）
- cache key = source.getKey() + ";" + javaClass.simpleName，source 任何字段变化都重建

## 六、关键设计事实（备忘）

- Android audioAvailable 按 maxBufferSize 分块写，AudioTrack 是最终背压源，整条链路靠它限速
- DirectPlayCallback 一直用挂起 send（与 PCM 的 trySendBlocking 现已一致）
- 静音 PCM 生成：onSynthesizeStart 已声明格式，onSynthesizeAvailable 必须发裸 PCM 不能带 WAV 头（44字节RIFF头会成噪音）
- 朗读规则 JS 引擎：Rhino，eval 在 textProcessor.init；多发音人 splitText 也走 JS
- maxSampleRate 取所有配置项 audioFormat.sampleRate 最大值，作为输出目标采样率，Sonic 负责重采样到它

## 七、0821 修订注记（对上文，不删改原文）

1. **预取时序（订正一、链路图 与 四、已修复#2）**：代码实际顺序是 `requestAndProcess(段N)` 完整返回后，才 `async` 发起段 N+1 预取（AbstractMixSynthesizer.kt:301-318）；而 requestAndProcess 受 trySendBlocking 背压会拖到段N接近播完。故 0818 预取的**有效窗口 ≈ 通道残存缓冲**，对所有插件形态（HTTP整包/挂流/WS攒发）都无差别地有限。真正的修法是"预取前移"（先发N+1再处理N，DirectPlay回调需按序入队），0821 未实施，原因见下面第4条。
2. **通道容量（订正 一、链路图 cap=32 与 四、已修复#5）**：0821 已将 PROCUDE_CAPACITY 32→128 块（≈256KB，24kHz下约5.5秒音频），本地提交 ffacfa7（未推送）。高倍速时 32 块盖不住插件网络等待；停止时通道直接丢弃，不影响停止响应。
3. **逗号二次切分（订正 五、未修复#1）**：已决策**不做**——切太细会削弱 TTS 依据上下文的情绪生成能力。此条关闭，勿再作为优化项提出。
4. **0821 分析范围外的补充事实**：醒锁 acquire 曾误写 2 分钟（ffacfa7 一并修复为 20 分钟）；四个声音插件的行为定性与并发安全矩阵（豆包/千问3652 V2攒发且并发不安全、火山/讯飞 V1 无状态）见会话记录；用户约束=不改任何插件 JS、1-2倍速为主流满意速度，预取前移+双引擎实例方案③整体挂起，触发条件=换攒发型插件当主力或上高倍速。
