## 一、先记住这三个不是同一个值

“采样率”在系统里有三个职责不同的来源。它们可以不同，且正常情况下不应互相覆盖。

| 名称 | 例子 | 谁决定 | 用途 | 是否当作每次实际音频的事实 |
|---|---:|---|---|---|
| **插件请求/声明采样率** | 插件界面选 MP3 + `48000` | 用户和插件 | 告诉服务端希望生成什么格式；也为裸 PCM 提供格式声明 | 否。服务端可能实际返回不同采样率的文件 |
| **实际返回音频的采样率** | 试听显示 `22050`、`audio/mpeg` | 音频文件头 | 解码、降混、重采样时的真实输入格式 | 是，但只对本次返回的音频流有效 |
| **配置项 PCM 声明/输出策略采样率** | `audioFormat.sampleRate = 48000` | 插件声明或已有配置 | 裸 PCM 的唯一格式事实；参与系统 TTS 统一 PCM 输出格式选择 | 不是 MP3/WAV/Opus 文件的实际采样率 |

因此下面的组合完全正确：

```text
插件界面：选择 MP3 + 48000
试听结果：实际返回 MP3 + 22050
配置项：保存插件声明 48000
播放：按实际文件头 22050 解码，再输出为系统 TTS 统一 PCM 格式
结果：时长、语速、音调正常
```

不能因为试听显示 `22050`，就手动把插件选择的 `48000` 改成 `22050`。

## 二、三条规则

### 规则 1：插件界面里选的采样率，以插件选择为准

插件自定义界面中的“音频格式”“采样率”等控件属于**插件请求参数**。

例如：

```text
音频格式：MP3
采样率：48000
```

它的含义是：插件向服务端请求 48 kHz 的 MP3，或选择插件定义的 48 kHz 输出档位。

插件状态通常保存在当前 `PluginTtsSource.data` 中，运行时由 `PluginTtsProvider` 交给插件引擎。插件通过 `EditorJS.getAudioSampleRate(locale, voice)` 声明当前声音/当前选项的采样率。

当前保存规则：

| 保存入口 | 写入 `audioFormat.sampleRate` 的来源 |
|---|---|
| 单条编辑保存 | 插件 `getAudioSampleRate()` 声明值；未声明时保留原配置的 PCM 兜底值 |
| 编辑页多选声音批量保存 | 每个声音的插件声明值；未声明时保留当前模板配置的 PCM 兜底值 |
| 按插件音色分类入库 | 新建插件引擎取得的插件声明值；未声明时使用模板默认值 `16000` |

> “按插件音色分类入库”是独立入口，没有当前编辑项的 `source.data` 可继承，因此它获取的是插件在新引擎中的默认/按声音声明，而不是某个尚未保存编辑页里的临时选择。

### 规则 2：有音频头的格式，播放时以实际音频头为准

以下格式带有可识别的格式信息：

```text
MP3 / WAV / Opus / WebM / AAC / …
```

播放时，程序会从本次返回的音频读取实际的：

```text
采样率 + 声道数 + MIME/编码格式
```

对于这些格式：

- 插件声明的 `48000` 不会强行把实际 `22050` MP3 当成 48 kHz 播放；
- 试听显示的 `22050` 仅表示这一次返回音频的真实格式；
- 实际检测值不会缓存，也不会写回配置项；
- 每次新的合成/下载结果都会重新识别。

### 规则 3：裸 PCM 没有音频头，必须相信配置/插件声明值

裸 PCM 没有 MP3/WAV 头，程序无法自动判断它到底是：

```text
16000 / 22050 / 24000 / 44100 / 48000 Hz
```

因此裸 PCM 的采样率必须由配置项 `audioFormat.sampleRate` 或插件声明提供，并且必须与源 PCM 的真实格式一致。

若裸 PCM 实际为 24000 Hz，却声明为 16000 Hz，就可能出现：

- 变慢或变快；
- 音调变粗或变尖；
- 重采样比例错误；
- 试听、标签桥接 WAV 包装和系统 TTS 输出不一致。

## 三、当前播放链

### 3.1 有音频头：MP3/WAV/Opus 等

```text
插件界面选择（例如 MP3 + 48000）
        ↓
插件请求服务端
        ↓
服务端返回实际音频（例如 MP3 + 22050 Hz + 双声道）
        ↓
解码器从音频头取得真实 22050 Hz、2 声道
        ↓
若多声道：先降混为单声道
        ↓
按真实输入 22050 Hz 重采样到本次系统 TTS 的统一输出采样率
        ↓
Android TTS：单声道 PCM-16，速度与时长正常
```

`DefaultResultProcessor` 中的运行时格式探测优先于配置里的数值；配置采样率只在没有音频头时才是输入格式的唯一事实。

### 3.2 裸 PCM

```text
插件返回裸 PCM（无文件头）
        ↓
不能探测真实采样率
        ↓
使用 audioFormat.sampleRate / 插件声明
        ↓
必要时重采样到系统 TTS 统一输出格式
        ↓
Android TTS：单声道 PCM-16
```

### 3.3 为什么系统 TTS 仍需要一个配置采样率

Android 的系统 TTS 回调不是“这一句 22050、下一句 48000”地分别声明格式。

一次合成请求开始时，程序必须向 Android 声明一个固定输出格式：

```text
sampleRate + PCM_16BIT + 单声道
```

`AbstractMixSynthesizer` 当前取所有已启用配置项 `audioFormat.sampleRate` 的最大值，作为这次系统 TTS 请求的统一输出目标采样率；每段音频会被转换到该目标格式。

这个值还用于生成：

- 段间静音 PCM；
- 失败兜底静音 PCM；
- 原始 PCM 的试听与 WAV 包装；
- 标签桥接取得原始 PCM 时的 WAV 头。

所以不能删除 `BasicAudioFormat.sampleRate` 字段，也不能把它简单改成“本次音频实际采样率”。

## 四、本地音效混合采样率的正确做法

“本地音效1”可以包含数百个不同格式的文件，例如：

```text
22050 Hz MP3
24000 Hz MP3
44100 Hz WAV
48000 Hz WAV
```

正确做法：

1. 插件中保留一个合理的请求/声明采样率，例如 `48000`；
2. 不要逐个音效手动填写或保存实际采样率；
3. 每次播放时让程序读取当前文件的音频头；
4. 由播放链自动降混和重采样到统一输出格式。

错误做法：

```text
试听发现某个文件是 22050
→ 把“全部音效”配置改成 22050
→ 下一个文件实际 48000，又改回 48000
```

混合采样率音效库不需要、也不应该使用一个配置数字去代表所有文件的实际格式。

## 五、为什么以前会出现 0.5 倍速

0.5 倍速不一定是“配置填 48000、文件是 22050”直接造成的。

本地音效问题中，关键情况是：

```text
文件：22050 Hz、双声道 MP3
旧系统 TTS 链：将左右交错的双声道 PCM 当作单声道 PCM 发送
结果：样本数量翻倍，播放时长翻倍，听起来约 0.5 倍速
```

已修复链路：

```text
读取真实声道数
→ 多声道先降混为单声道
→ 再进行采样率转换
→ 按系统 TTS 声明的单声道 PCM 输出
```

相关提交：

| 提交 | 内容 |
|---|---|
| `091e0da` | 对有音频头的格式，播放时优先使用真实采样率 |
| `db20729` | 使用专用线性插值重采样器，移除 Sonic `rate` 的错误用途 |
| `91251d3` | 立体声音效先降混，修复系统 TTS 路径的慢一半问题 |
| `9c73e9e` | 分离插件声明采样率与试听/实际音频采样率，不再逐声音测率写回配置 |

## 六、试听、批量保存与分类入库的现行规则

### 6.1 试听

试听弹窗仍显示：

```text
音频大小
音频采样率（本次返回音频的实际值）
音频格式/MIME
```

例如：

```text
音频采样率：22050
音频格式：audio/mpeg
```

这只是诊断信息，回答“服务端这一次实际给了什么”。它不会：

- 修改插件界面选择；
- 缓存到发音人；
- 修改现有配置项；
- 决定以后别的声音如何播放。

### 6.2 批量保存/分类试听保存

旧逻辑会：

```text
试听测到的实际采样率
→ 缓存到 voiceSampleRateCache
→ 必要时再为每个声音合成一次
→ 从音频头测率
→ 写进每一个新配置项
```

现行逻辑已删除该流程：

```text
插件声明采样率
→ 写入配置项

实际 MP3/WAV/Opus 格式
→ 以后每次播放时再读取音频头
```

因此批量保存大量声音不再因为“只为测采样率”而为每个声音多请求/多合成一次。

### 6.3 按插件音色分类入库

分类入库同样不再合成每一个声音读取音频头。

它仍逐声音读取 `isNeedDecode`，因为这决定该声音是否是可解码音频还是裸 PCM；采样率则采用插件声明值或安全兜底值。

## 七、界面展示规则

### 配置列表卡片

| 实际播放路径 | 卡片显示 |
|---|---|
| 可解码格式（MP3/WAV/Opus 等） | `自动识别格式` |
| 裸 PCM | `PCM 16000 Hz`、`PCM 24000 Hz`、`PCM 48000 Hz` 等 |

这避免把旧配置里存的 `16000 / 24000 / 48000` 误解成“当前这段 MP3 的实际采样率”。

本地 TTS 还会结合“直接播放”开关判断真实路径：关闭直接播放时会走原始 PCM 路径，因此卡片会显示 `PCM N Hz`，不会错误地显示“自动识别格式”。

### 本地 TTS 编辑页

原来的泛称“采样率”字段已改为：

```text
PCM兜底采样率（Hz）
```

问号说明的含义：

- MP3/WAV/Opus 等会自动识别实际格式；
- 裸 PCM 必须填与源音频一致的值；
- 此值参与系统 TTS 的统一 PCM 输出格式选择；
- 不影响插件自定义界面中选择的音频格式或采样率。

插件自己的 UI（例如“音频格式：MP3”“采样率：48000”）保持原样，仍属于插件请求参数。

## 八、用户操作速查

### 正常插件：返回 MP3/WAV/Opus

```text
1. 在插件界面选择服务端支持的格式和采样率，例如 MP3 + 48000；
2. 正常保存即可；
3. 不要根据试听显示的 22050/24000 去反复改配置；
4. 列表看到“自动识别格式”属于正常状态。
```

### 本地音效：文件采样率混合

```text
1. 保留插件自己的声明/选择；
2. 不要逐个音效保存 22050、24000、48000；
3. 试听信息只用于确认文件实际格式；
4. 朗读路径会按每个文件的真实音频头处理。
```

### 裸 PCM 插件或本地 PCM 音源

```text
1. 确认插件是否标记为无需解码；
2. 确认 PCM 真实采样率；
3. 使插件声明/配置项 PCM兜底采样率与真实 PCM 一致；
4. 列表应显示“PCM N Hz”，而不是“自动识别格式”。
```

## 九、排错表

| 现象 | 优先检查 | 处理方向 |
|---|---|---|
| 试听正常，系统 TTS 朗读慢一半 | 返回文件是否双声道；系统版本是否包含降混修复 | 不要先改 22050/48000；检查声道处理和版本 |
| 某个 MP3 实际 22050，但插件选 48000 | 正常 | 插件值是请求/声明，播放时文件头 22050 会自动生效 |
| 裸 PCM 变快、变慢或变调 | PCM 真实采样率与配置声明是否一致 | 将 PCM兜底采样率设为真实 PCM 值 |
| 列表显示“自动识别格式” | 正常 | 表示这条配置走可解码音频路径，实际格式播放时识别 |
| 列表显示“PCM 16000 Hz” | 正常，但需要确认 | 表示该配置按裸 PCM 处理，16000 必须是源 PCM 的真实值 |
| 批量保存很慢 | 不再应由“测采样率”造成 | 检查插件拉取声音、规则脚本、数据库写入或网络请求 |

## 十、维护约束

1. **不改插件 JS**：插件 UI 的格式/采样率选择属于插件自身协议与状态；app 侧只区分声明值和实际音频头。
2. **不要恢复逐声音合成测率**：它会让批量保存变慢，并错误地把一次返回音频的瞬时格式写成长期配置事实。
3. **不要删除 `BasicAudioFormat.sampleRate`**：裸 PCM、WAV 包装、系统 TTS 统一输出和静音 PCM 都需要它。
4. **不要用 Sonic `rate` 做采样率转换**：Sonic `rate` 会改变速度和音调；采样率转换由 `SampleRateResampleProcessor` 完成。
5. **旧配置无需批量迁移**：旧的数值仍保留以兼容裸 PCM 和输出策略；对可解码音频，卡片不再把它显示成文件真实采样率。
