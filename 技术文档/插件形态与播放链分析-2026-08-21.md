# 插件形态与播放链分析（2026-08-21）

> 背景：直连播放链（不开转发器）的一次完整审计。插件 JS 原件不在仓库（为用户附件），
> 本文固化其行为结论；代码链路结论同步见 tts配套文件/播放管线技术研究.md 及「0821 修订注记」。

## 一、四个声音插件的行为定性

| 插件 | 类型 | 传输形态 | 并发安全 | 关键行为 |
|---|---|---|---|---|
| 火山翻译(2026) | V1 getAudio | 单 POST 整包 base64 | ✅ 无状态 | speed/pitch 被 JS 丢弃 →「插件处理参数」开关**别勾** |
| 讯飞配音(实时) | V1 getAudio | 两跳签名 HTTP 整包 | ✅ 无状态 | 流式分支是死代码（`ttsrv.httpGetStream` 不存在）；speed/volume 服务端生效 → 开关**要勾** |
| 豆包-猫箱 | V2 getAudioV2 | WS 长连，攒齐后一次回调 | ❌ 全局单例 | 按 voiceId 绑定 WS，切角色重握手；并发会被拒且误杀在播段 |
| 千问3652 | V2 getAudioV2 | WS 攒发（每块 base64 攒 chunks） | ❌❌ 无防护 | **每段 flushAllAudio 后 ws=null，必重新握手**；并发会静默串音；PCM 模式每段自带前后 200ms 静音填充；`__jreadPcmStreamBridge` 在本 app 不存在，永远走攒发 |

「并发安全」列决定预取前移方案的门：✅ 可直接并行预取下一段；❌ 必须同 pluginId 双引擎实例隔离，否则串音/报错。

### 桥接流式判定速查（TtsPluginEngineV2.handleAudioResult 按返回类型）

| JS 返回 | 效果 |
|---|---|
| InputStream | 直通流式 |
| http.get/post 的 NativeResponse → `.body.byteStream()` | 流式（懒消费 body） |
| ByteArray / NativeArrayBuffer / NativeTypedArrayView | 全量缓冲（内存攒齐才播） |
| http 开头的 String | 当作 URL 下载，流式 |
| 裸 `ttsrv.httpGet()/Post()` 的 Response | **不识别**，不会被当音频流 |
| `ttsrv.httpGetStream` | **不存在此 API**，调用即走 fallback |

## 二、预取时序错位（段间空隙的机制详解）

AbstractMixSynthesizer 段循环的真实顺序：

```
await(prefetchJob)            ← 等上一圈发出的 N 段请求
requestAndProcess(N)          ← 解码+管线+trySendBlocking 写通道,
                                受背压拖到段N接近播完才返回
async { requestInternal(N+1) } ← 之后！才发出下一段请求
```

结论：**N+1 的请求发出时机 ≈ 段N快播完**，有效重叠窗口只剩通道里残存的缓冲。
0818 版「预取消除段间等待」只兑现了这一小截；对 HTTP 整包、挂流、WS 攒发**三种形态一视同仁地有限**。
这正是 Section 一里各插件段间表现趋同的原因。

**修法（已决策挂起）**：先发出 N+1 再处理 N（预取前移），DirectPlay 回调需按序入队。
配套并发门：V1 无状态插件直接放行；V2 按 pluginId 起第二个引擎实例做隔离。
触发条件：换攒发型插件当主力、或上高倍速觉得段间硌耳。

## 三、hunyuan ↔ mumu 播放差异对照（同样的插件和设置为何体感不同）

| 维度 | hunyuan | mumu | 听感影响 |
|---|---|---|---|
| 段间调度 | 纯串行，每段播完才请求下一段 | 预取（窗口有限但非零）+ 通道背压 | mumu 段间死寂大幅缩短 |
| 语速来源 | 插件级滑块非 0 时**覆盖**配置项 | 插件级 × 配置项**相乘** | 插件级滑块非 0 的用户两边结果不同 |
| 流式播放默认值 | 开 | 关 | 开流式时网络抖动造成句内顿挫；mumu 整段下完再播更连贯 |
| 插件自处理语速 | 无此概念，永远 Sonic 本地变速 | 有「插件处理语速/音量」开关，勾上则服务端变速、Sonic 跳过 | 同一插件两边可能变速路径不同 |
| 响度均衡 | 无 | 恒开（自动学习发音人增益） | 音量齐整度不同，间接影响节奏感 |

## 四、用户约束与已决策项（勿再翻案）

- **不改插件 JS**（十几个插件，工程量不现实）——优化只走 app 侧/配置开关/用户自己调规则。
- **分句不切逗号**：切太细削弱 TTS 依据上下文生成情绪的能力。
- **规则 `bingfa` 并发不调**：那是同段文本多次 AI 判断投票取准确性的机制，与速度无关。
- **段间停顿=固定墙钟时长**：不随语速缩放（1x 与 3x 下听感一致的问题日后再说）。
