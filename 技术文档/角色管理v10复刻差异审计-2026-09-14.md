# 角色管理 v10 复刻差异审计（2026-09-14）

## 0. 为什么要做这次审计

09-14 书籍改名出现「新旧书名同时在列表、每改一次多一条」。复盘发现：号称「1:1 复刻 v10」的实情是**逐函数读 JS 写 Kotlin**，不是逐行对照；且有自写 helper 把原版语义顶掉了（`readBookList` 自加「当前书不在列表→补头部」兜底，而 v10 的 `getBookList()` 是直读 json 无兜底）。**致命点**：那个 helper 写于复刻之前（`5ad3234` 19:07 全套内置 → `ede2ec0` 20:27 复刻），复刻时是站在一个「已经不是 v10」的底座上写，拿单个函数去对 JS 永远看不出差异。

于是按同一方法对整条功能链做一次全量复核。

**范围**：只审功能/数据逻辑，**不含 UI、布局、主题**。
**对照物**：`tts配套文件/角色管理v10_主题密钥增强.js`（8392 行，171 个 function）
**Kotlin 侧**：`CharacterRecordsFile.kt`(733) / `KeyListFile.kt`(408) / `KeyManagerScreen.kt` 与 `VoicePickerDialog.kt` 里的数据逻辑
**方法**：函数清单逐条对位 → 逐段读原版实现 → 可疑处用 Python 把两边逻辑 1:1 复现跑对照

分级口径：
- **P0 高**：会让用户得到错误结论、或造成数据丢失/污染、或功能等于不存在
- **P1 中**：特定操作序列下行为不一致，用户能察觉
- **P2 低**：细节口径差异，一般感觉不到
- **S**：结构性差异（无对应实现 / 存储介质不同）

## 1. P0 高危（9 条）

### P0-1 密钥测试策略倒置 → 「假可用」
- 原版 `testModelKey`(797-838)：**先 POST `chat/completions`** 并用 `chatReplyOk` 校验响应体，失败才降级重试（去 `max_tokens`/`temperature`）；`/models` **只在失败后作为参考提示**，且返回里明写「该端点多数站点不校验密钥，不能说明密钥可用」(836)。
- Kotlin `KeyListFile.testKey`(282-294)：**先 GET `/models`，`resp.ok` 就 return true**，完全不看 body。
- 后果：多数中转站 `/models` 对任意 key 都返回 200 ⇒ **错的密钥也显示"可用"**。这是原版注释专门警告过的坑。
- 修法：按原版改成 chat 优先 + body 校验 + 降级重试；`/models` 降级为参考文案。另需补 401/403、404、400 的分级文案。

### P0-2 `keyBelongsTo` 丢了 key 比较 → 删接口会误删同站其他密钥
- 原版 `keyBelongsTo`(2457-2461)：`sameApiSite(pv.url, ifc.baseUrl) && pv.key === ifc.apiKey.trim()`。
- Kotlin `KeyListFile.kt:307-310`：**只判同站**，`&& key 相同` 这一半没了。
- 后果：同一站点下存在两把不同 key 时，删除接口 A 会级联删掉属于 B 的密钥（`deleteInterfaceCascade` kt:313）；密钥分组也把 B 归进 A。

### P0-3 拉取模型把对象当字符串 → 模型名变成一坨 JSON
- 原版(606-617)：取 `data[].id`（也兼容裸字符串数组 / `models` 字段）。
- Kotlin `KeyListFile.fetchModels`(265-276)：`JSONArray.optString(i)` —— 标准 OpenAI `{"data":[{"id":"gpt-4o"}]}` 下 `optString` 把**整个对象 toString** 取出来，于是"模型名"= `{"id":"gpt-4o","object":"model",...}`，写进密钥 model 段后作废。
- 附带：Kotlin 多了 `sorted()`（原版保持返回序）。

### P0-4 新增/覆盖密钥会静默切走当前密钥
- 原版(2336/2352)：**仅当当前密钥为空时**才写 `miyue.txt`。
- Kotlin `KeyManagerScreen.kt:714 / 748`：新增/覆盖后**无条件三写**。
- 后果：正在用 A 朗读时新增 B，当前密钥被静默切成 B。

### P0-5 合并角色丢掉被并记录的别名
- 原版 `doMergeOperation`(7504-7534)：收集「目标别名（无别名则退回主名）」+「每个被并记录的别名（无别名则退回其主名）」，`normalizeString` 规范化去重后 `join('|')`。
- Kotlin `mergeCharacters`(255-266)：只取 `目标别名 + mergeNames(名字)`，**完全不读被并记录自己的 aliases**。
- 后果：把「A（别名 a1、a2）」并入「B」→ 原版 B 的别名含 a1、a2；Kotlin 得到的是字面 "A"。之后按 a1 朗读匹配 / 搜索都找不到 B。
- 附带：原版存的是规范化小写名，Kotlin 存原样大小写。

### P0-6 删除角色按名字删 → 同名两条一起消失
- 原版 `doDeleteCharacterOperation`(7915-7935)：按**标记的索引**筛，只删被标记的那一条。
- Kotlin `deleteCharacters`(220-227)：`filter { it.name !in names }`，**同名记录全删**。
- 后果：插件侧 `+添加角色` 不查重、允许文件里存在同名多记录（AI 规则写入也可能造成）。用户想删其一，结果两条都没了。

### P0-7 导入书籍少两步 → 书会消失、且被下次朗读覆盖回去
- 原版 `restoreFromText`(5008-5040)：写文件之外还调 `updateBookList`(5031) 与 `createGengxinFile`(5035)。
- Kotlin `KeyManagerScreen.kt:1463-1481`：只写 `cunfang.txt / characterRecords.json / shuming.<书>.json`。
- 后果：①该书从未进 `liebiao.json` → 切走再回来书从书架消失（`readBookList` 只兜当前书）②不写 `gengxin.json` → 朗读规则内存仍是旧角色表，**下次朗读会把导入的数据覆盖回去，导入白做**。
- 附带：这段还硬编码了绝对路径 `/storage/emulated/0/Download/chajian`，没走 `BASE_DIR`。

### P0-8 备份清单缺两个文件
- 原版 `backupAllFilesToData`(4816-4821) 备 8 项，含 **`voice_marks.json`、`custom_keywords.json`**。
- Kotlin `CharacterRecordsFile.backupAllFiles`(653-674) 备 7 项：`characterRecords / liebiao / cunfang / fayinren / key_list / miyue / api_center` —— **多备 `api_center`（无害），少备标记与自定义关键词**。
- 后果：用户「备份 → 改动/清现场 → 恢复」后，❤️🚶😈 标记与自定义关键词回到现场值，不是备份值。
- 附带：原版对角色数据还会**逐条删掉 `genderAgeHistory` 字段**再落备(4828-4842)；Kotlin 原文入备。

### P0-9 纯 Key（直连）密钥永远测不了
- 原版 `testModelKey`(798-806)：`parseKeyForTest` 把纯 key 判为 `zhipu` 分支，走智谱 `/models` 可测。
- Kotlin `KeyManagerScreen.kt:312`：`isDirect` 直接拒绝测试。
- 后果：只填 key 的直连条目没有可用性检验入口。

## 3. P2 细节（9 条）

1. **`norm()` 只 `trim()`** vs 原版 `normalizeString`(3687)=去零宽字符 `\u200B-\u200D\uFEFF` + `trim` + `toLowerCase` ⇒ 含零宽字符/仅大小写不同的书名、角色名不会被判重（中文场景少见）。**影响面很广**：改名、删除、去重、成员比较全用它。
2. `classifyModel`(kt:398) 词表与原版(1901) 有出入：原版的 `babbage/rerank`、`diffusion/midjourney/sdxl/sd3/cogview/kolors/janus`、`vidu/cogvideo`、`transcri/cosyvoice` 缺失；Kotlin 自加 `bge`、`draw/paint/stable/sd`、`runway` ⇒ rerank、midjourney 等会落进"文本"。
3. `getOpenAiBaseUrl`(kt:212-222)：原版(283-293) 命中 `/chat/completions|/completions|/models` 后缀后**直接 return**（不再补 `/v1`），Kotlin 先剥后缀再补 ⇒ base 带后缀时基址不同，`sameApiSite` 判同站被放宽。
4. 性别圆点取的是**发音人标签文本**（`RoleListScreen.kt:771` 传 `rec.voice`，`genderDotColor` 86-91 靠关键词匹配，还自加 `contains("少年")`），原版 `generateDisplayName`(2786-2792) 取记录自身的 `gender` 字段 ⇒ Kotlin 侧 `gender` 字段实际无人读。
5. 搜索范围：原版(8019-8031) 匹配 name/aliases/gender/age/voice 五字段，Kotlin(164-167) 只 name + aliases。
6. 池顺序与空池兜底：原版 `refreshFayinrenList`(189-206) 读后按「类别+序号」排序、池空回落 `["默认发音人"]`；`readVoicePool`(27) 原序返回、无兜底。
7. 语音标记按 **voice** 分存（`VoiceMarksFile.marksFor` 93-96 "voice 优先、tag 兜底"），原版只有 tag 键 ⇒ 旁白类（tag=`narration`）与插件不互通；`readAll` 遇到数字值会产出 `["5"]`（原版置 `[]`）。
8. 占用计数：原版 `getVoiceAssignedCount`(6580-6586) 严格 `voice === tag`（不 trim、空名也算），`readVoiceOwnerMap`(65-83) 两侧 trim 且跳过空值。
9. 主角皇冠位置：原版(2808-2810) 👑 在**最后一行别名之后**，Kotlin(`RoleListScreen.kt:776`) 只在首行主名后。

## 4. 结构性差异（S，非 bug，登记备查）

- **存储介质**：原版把密钥表、书单、当前书、自动备份开关同步进框架持久存储 `tts.data`（`bookListData` / `currentBookName` / `currentKeyName` / `autoBackupEnable` / `backupTest`），Kotlin 无此介质，一律落文件（`fullBackup.json` / `autoBackupEnable.txt`）。原版 `getKeyMapFromData` 的旧格式回落 `tts.tts.data.keyListJson`(2584) 亦无对应。
- **`ensureApiCenter`(2464) 无对应**：无 `api_center.json` 时原版用现有 `@@` 密钥自动聚合成"接口N"；Kotlin `readInterfaces` 直接返回空。
- **`isCurrentKeyItem`(929) 的"按名称优先"分支缺失** ⇒ 同 value 不同名会双高亮。
- **接口 `models` 字段**：原版拉取/手填会回写、删条目同步移除；Kotlin 只读不写，恒空。
- **备份书籍存档枚举**：原版按 `liebiao.json` 书单逐个取，Kotlin 用 `listFiles()` 扫 `shuming.*.json` ⇒ 多备孤儿存档。
- **`switchBook` 与原版 `useBook`(4227) 的两点差异**：①原版 **不动** `characterRecords_backup.json`（保持上一本书数据），Kotlin 写成新书数据（**Kotlin 更安全**）②原版 `useBook` 完全不碰 `liebiao.json`，Kotlin 会补录并头插。
- **Kotlin 自加、原版没有的 API**：`releaseAlias`(272)、`removeAlias`(293)、`renameCharacter`(210)、`readCharacterVoice`(42)、`unbindVoice`(612) —— 其中前三个全仓无调用方。
- **字符串编码/格式**：Kotlin 落盘缩进 2 空格、原版部分处 compact（可解析，非 bug）。

## 6. 建议的修复批次

**第一批（P0，9 条）**——直接影响"密钥到底能不能用"和数据完整性，建议优先：
P0-1 测试策略、P0-2 keyBelongsTo、P0-3 拉取模型、P0-4 miyue 三写、P0-5 合并别名、P0-6 删除粒度、P0-7 导入书籍补两步、P0-8 备份清单、P0-9 直连测试。

**第二批（P1）**——行为一致性；其中 P1-5（rebind 备份）、P1-8（启动自愈）、P1-9（导出文件名）建议一并做。

**第三批（P2）**——`norm()` 对齐（一旦改，会影响改名/删除/去重多处，需单独验证）等细节口径。

> 铁律（本次教训）：凡模块里有自写 helper，复刻前必须先审 helper 是否等价原版；改数据链逻辑一律先把两边逻辑 1:1 搬成脚本跑连续操作对照，再动手。
